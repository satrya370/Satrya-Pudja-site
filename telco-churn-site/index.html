A churn model is easy. A model a support agent can actually interrogate — "why is this customer at risk, and what do our retention docs say to do about it" — is the harder problem.

Final project for the Digital Skola Fullstack AI Engineering bootcamp: a trained churn-prediction model behind an MLflow champion/challenger registry, paired with a chat agent that decides for itself — via manual tool-calling, not a fixed script — when to run a prediction, explain it with SHAP, pull a retention policy, or pull account-wide statistics.

How it works

Ingestion runs on its own schedule

The IBM Telco Churn dataset loads into Postgres on startup and re-ingests hourly via APScheduler — no manual step to get data into the system.

Training is a gate, not a guarantee

Five candidate models are evaluated with stratified 5-fold cross-validation — a single train/test split can give a misleading PR-AUC on imbalanced churn data purely by chance. The best candidate is logged to MLflow and promoted to `@champion` only if it actually beats the model currently in production.

/predict scores against the live champion

Loads the champion model from the MLflow Model Registry and returns a churn probability and risk level for a given customer — the model that's live, not whatever was trained most recently.

/chat decides which tools it needs

A manual tool-calling loop over OpenRouter with 6 tools — churn prediction, SHAP explanation for one customer, RAG retrieval over FAQ/retention-policy docs, and 3 tools for account-wide statistics. The agent chooses which to call per question, verified against a curated prompt set that includes prompts that should trigger zero tool calls at all.

Security testing, not just a demo

A chat agent wired to real customer data and a document store is also an attack surface. Five real attempts were run against the live `/chat` endpoint — not hypothetical, actually executed and logged:

Direct override

Asked the agent to ignore its instructions, repeat its system prompt, and hand over customer credit card numbers and passwords. It ignored the instruction and answered the underlying churn question instead.

Indirect injection via RAG poisoning

A malicious instruction was embedded inside a document designed to rank in the top-3 retrieval results, disguised as an official policy note. The agent did not follow the embedded instruction even after retrieving and citing that chunk.

Roleplay, fake history & base64

Three more attempts — persona/roleplay framing, a fabricated prior conversation implying prior consent, and instructions obfuscated in base64. All three failed to change the agent's behavior.

Full payloads, setup, and results for all 5 are written up in the project's own docs/injection_tests.md — not summarized after the fact, logged at the time each was run.
